## このスキルの責任範囲

- このスキルは、法令およびエアワーク公開規約に照らして**高リスクの候補を検出する**。
- 「検出されなかった＝掲載可能」ではない。媒体には非公開の審査基準が存在する。
- **最終的な掲載判断は必ず人間が行う。**
- このスキルは事実条件（給与額・勤務時間・勤務地・雇用形態）を変更しない。
  変更するのは、同じ事実をどう伝えるかという表現層とタグ層のみ。
- 分析工程（lint・タグ棚卸し・訴求案生成）はネットワークへ出ず、入出力を`/tmp`だけに限定する。
- 外部へ書き込むのは次の2か所だけである。

| 工程 | 書き込み先 | 動作 |
|---|---|---|
| 手順0 | ヒアリング履歴スプレッドシート | **行を追記**する（`hearing_log.py append`）。既存行は書き換えない |
| 手順5 | 出稿用Googleドキュメント | 指定フォルダに**新規作成**する。既存ファイルを上書きしない |

  手順0の追記は**省略しない**。ここを飛ばすと次のセッションで同じ質問を繰り返すことになり、
  このスキルの目的（フロントに二度同じことを聞かせない）が達成できない。
  Joblist・内容確認書・求人媒体は読むだけで、書き換えない。媒体への入稿は人間が行う。
- `CANDIDATE`、`MISSING`、`CONFLICT`を文面生成の根拠に使わない。生成案はR1〜R10で再lintし、`HIGH_RISK`案を出力本文から除外する。
- タグ棚卸しと文面テストを同時に行わない。A案からE案も同一求人で同時掲載しない。
- ヒアリングで答えが返らなかった項目を推測で埋めない。未回答は欠陥ではなく想定内の状態として扱い、
  その項目を原稿に使わないまま完成させる。詳細は`references/hearing-protocol.md`。

## 使う前に

1. 初回は`SETUP.md`を上から順に読み、Codex、Node.js 20以上、Python 3、スキル配置を確認する。
   **`SETUP.md`手順3でGoogleドライブ側の実体（Joblist・内容確認書・ヒアリング履歴・出稿用フォルダ）を
   先に用意する。**スキルを置いただけでは何も読めない。
   **Windowsの場合はWSL2（Ubuntu）の中で動かす。**このスキルは実データを`/tmp`だけに置く設計で、
   PowerShellネイティブには`/tmp`が無いため最初のコマンドで止まる。`uname`が`Linux`を返さない、
   または`must be a file below /tmp`が出たら、それ以上コマンドを試さず、
   Codexの Settings を`Windows native`から`WSL`へ切り替えてアプリを再起動するよう案内する
   （手順は`SETUP.md`手順0）。**この状況でスクリプトを書き換えて回避しない。**
2. **クライアントの初期設定をする。新しい会社を追加するときは必ずここから始める。**

```bash
python3 scripts/init_client.py --client foot          # 対話。既存値はEnterで据え置き
python3 scripts/init_client.py --client foot --check  # 設定は変えず疎通確認だけ
```

Joblist・内容確認書・ヒアリング履歴・出稿用ドキュメントの保存先フォルダの4つを聞き、
**実際にアクセスして開けるか・書けるかを確かめてから**`references/clients/{client}/config.json`に書く。
共有URLをそのまま貼ってよい（IDだけ抜き出す）。

- 新しい会社は`--client newco`と打つだけで`references/clients/newco/`がfootから複製される。
  ただし**`question-catalog.json`の層1は「その会社の方針」**（性別タグを出すか等）なので、
  コピーのまま使わない。実行時にも警告が出る。
- **ヒアリング履歴は会社ごとに別ファイルにする。**1ファイルにまとめてタブで分けない。
  ドライブの共有はファイル単位なので、1社に共有すると他社のタブまで見える（`SETUP.md`手順3）。
- 4項目すべてに`[OK]`が並ぶまで先へ進まない。ここで落ちるのはたいてい共有権限が「閲覧者」になっている。
- 先頭に「いまどのアカウントでAPIを叩いているか」が出る。想定と違うアカウントなら止める。
  サービスアカウントで運用する場合は、4つの対象をそのアドレスに**編集者**で共有しておく。

3. Joblist CSVを作る。**手でダウンロードしない。登録済みのスプレッドシートから毎回作り直す。**

```bash
python3 scripts/export_csv.py --client foot
# → /tmp/foot_joblist_YYYYMMDD.csv
```

`/tmp`にCSVが無くても**ここで止まらない。**上のコマンドで作る。手で落としたCSVがあれば
それでもよいが、古い可能性があるので基本は作り直す。

CSVになるのは**Joblistだけ**である。Joblistを読む2本（`preflight` / `read_joblist`）が
Node製でGoogleの認証を持っていないので、認証をPythonに一本化してNodeへはCSVを渡す。
**Joblistは239列で渡す**（265列目の求人メモには単価が入っており、
Node側は使わないので渡さない。`fetch_current.py`だけが読み、そこで伏せ字にする）。

**内容確認書はCSVにしない。**読む側の`scripts/read_contract.py`がPythonで認証を持っており、
CSVを挟む理由がない。さらにCSVにすると、読まないと決めている**行35（年齢・性別・国籍）が
物理的にファイルへ書き出されてしまう**。`read_contract.py`は`contract-map.json`が許可した
範囲だけを`values.batchGet`で要求するので、行35はそもそもGoogleから返ってこない。
運用ルールではなく構造で守るために直読みにしてある。

4. preflightを実行する。内容確認書はスプレッドシートを直接見るので指定は不要。

```bash
node scripts/preflight.mjs \
  --client foot \
  --joblist /tmp/foot_joblist_YYYYMMDD.csv
```

すべての必須検査が`OK`なら先へ進む。`NG`が1件でもあれば、表示された直し方に従って入力を用意し直す。

- 検査8（内容確認書マップ・行35）は`read_contract.py --check-map`を呼ぶ。通信しない。
  `contract-map.json`に行35を含む範囲があれば`NG`で止まる。
- 検査9（内容確認書 疎通）は`read_contract.py --probe`を呼ぶ。セルの値は1つも読まない。
  認証やネットワークが無い環境では`WARN`になるが、preflight全体は止めない。

入力を正規化する。

```bash
node scripts/read_joblist.mjs \
  --csv /tmp/foot_joblist_YYYYMMDD.csv \
  --client foot \
  --output /tmp/normalized.json

python3 scripts/read_contract.py \
  --client foot \
  --output /tmp/contract.json
```

## 0. 依頼を受け取り、対象求人を特定し、ヒアリングする

フロントは次の7項目で依頼を投げる。**案件番号は含まれない。案件番号はスキルが引き当てる。**

```
■ 派遣先        ：◯◯運送
■ 事業所        ：◯◯営業所
■ 職種          ：4tトラックドライバー
■ 任せる仕事     ：部品の輸送。市内の工場3か所を回る
■ 勤務時間・シフト：8:00-17:00
■ 時給          ：1500〜1875円
■ 採用予定人数   ：2名
```

- **7項目が渡されていない状態でこのスキルが呼ばれたら、上のフォーマットをそのまま提示して記入を求める。**
  フロントが貼り忘れていることが多い。「入力がないので実行できません」で止めない。
  疎通テストや自己テストだけを実行して終わらせない。**足りないのは入力であって、聞けば出てくる。**

```
求人原稿を作ります。下記フォーマットに記入してお送りください。

■ 派遣先        ：
■ 事業所        ：
■ 職種          ：
■ 任せる仕事     ：
■ 勤務時間・シフト：
■ 時給          ：
■ 採用予定人数   ：

案件番号は不要です。こちらでJoblistから引き当てます。

（任意）AirWorkの有料広告の実績データがあれば、スプレッドシートのURLもお送りください。
どの欄を直すと応募が増えるかを数字から判定します。無くても原稿は作れます。
```

- **広告実績は任意。**渡されなければ手順0-3を飛ばす。**無いことを理由に着手を止めない。**

### 0-1. 依頼そのものが矛盾していないかを、質問より先に見る

**7項目を受け取ったら、Joblistを引く前にここを通す。**
矛盾したまま先へ進むと、A案からE案まで同じ矛盾を抱えたまま出てくる。
あとから直すと5案とも作り直しになる。**質問の前・案作りの前に止める。**

いちばん多いのは**■職種と■任せる仕事の食い違い**。両者は同じ仕事を別の粒度で書いた欄なので、
片方が屋内に閉じていて、もう片方が外を動いていたら、どちらかが間違っている。

| ■職種がこの系統なら | ■任せる仕事にこれが出てはいけない |
|---|---|
| 倉庫内／構内／工場内／センター内／ライン／組立／検査／ピッキング／梱包 | 配送／輸送／納品／集荷／巡回／ルート／◯か所を回る／ドライバー |
| ドライバー／配送／輸送 | 倉庫内のみ／構内のみで完結する作業 |

同じ見方で次も確認する。

| 見るところ | 食い違いの例 |
|---|---|
| ■勤務時間・シフト と 仕事の性質 | `8:00-17:00`固定なのに任せる仕事が「シフト制」「夜勤あり」 |
| ■時給 と 職種 | レンジ幅が広い（例 1500〜1875円）のに、何で上限に届くのかが依頼のどこにもない |
| ■採用予定人数 と 任せる仕事 | 1名募集なのに「チームで」「複数名で分担」 |

**見つけたら、自分でどちらかに寄せて書かない。混ぜて書くのはもっと悪い。**
「倉庫内フォークリフト作業」と「西尾市内の工場3か所を回る」を両方入れた原稿は、
求職者にどちらの仕事か伝わらないまま応募させることになる。面接で食い違えば早期離職につながる。

止めるときはこの形で返す。**質問リストの1問目に混ぜない。**混ぜると他の質問と同じ重さに見える。

```text
先に1点だけ確認させてください。いただいた依頼のなかで、
■職種 と ■任せる仕事 が食い違っています。

  ■職種      ：倉庫内フォークリフト作業   → 倉庫の中で完結する仕事
  ■任せる仕事 ：西尾市内の工場3か所を回る  → 外を移動する仕事

どちらが実態でしょうか。ここが決まらないと、5案とも食い違ったまま出てしまいます。

  A. 倉庫内フォークリフト作業（移動なし）
  B. 4tトラックでの輸送（3か所を回る）
  C. 両方ある（時間配分も教えてください。例：午前は輸送・午後は倉庫内）

決まりしだい、残りの確認と5案の作成に進みます。
```

- **ヒアリング履歴に前回回答があっても免除しない。**履歴が答えているのは「前回はどちらで出したか」であって、
  今回渡された依頼文が矛盾している事実は消えない。前回と同じ結論になるとしても、
  依頼文が矛盾しているなら毎回指摘する。**フロントの書き間違いは毎回起こる。**
- 矛盾が1件だけなら、ここで止めても往復は1回増えるだけ。5案を作り直す往復より軽い。
- フロントが「Cで両方ある」と答えたら、**どちらを主に据えるかまで決めてから**書く。
  職種名（No.3）とキャッチ（No.33）で主従が入れ替わると、同じ原稿の中で仕事が2つあるように読める。

- **■派遣先が空の依頼は処理を進めない。**既存求人のどれを直すのか特定できない。
- 案件番号は**目で探さない。**次のコマンドで引き当てる。**`--title`に■職種をそのまま渡す。**

```bash
python3 scripts/hearing_log.py resolve --client foot \
    --site 派遣先名 --office 事業所名 --title 職種
```

  Joblistの列に派遣先名は無い（勤務地名は全件`FooT株式会社`＝派遣元）。派遣先は
  **求人メモ欄にしか書かれていない**うえ、メモ欄は単価が入るのでCSVには渡していない。
  だから目で探すと必ず取り違える。このコマンドはスプレッドシートを直接見る。

  - **1件ヒット＋職種一致** → その案件番号を手順5のタブ名に使う。
  - **1件ヒット＋職種が不一致** → **その案件番号を使わない。**派遣先が同じでも別の仕事である。
    `⚠ 依頼された職種に一致する既存求人がありません`が出たら、
    「既存求人のリライトか、新規案件か」をフロントに確認してから進める。
  - 複数ヒット → 案件番号・職種名・勤務地を並べてフロントに選ばせる。**推測で選ばない。**
  - 0件 → 新規案件として扱う。タブ名は`YYYYMMDD_派遣先名`の仮名を使い、
    AirWorkで採番されたあとに案件番号へリネームする。

- **ヒアリング履歴に案件番号があっても、それだけで確定しない。**履歴が示すのは
  「その派遣先で前回どの案件を扱ったか」であって、今回の依頼が同じ仕事だとは限らない。
  同じ派遣先に別の職種の依頼が来るのは普通のことである。必ず職種で照合する。

### 0-2. 依頼の条件と、いま掲載中の条件が食い違っていないか見る

案件番号が決まったら、**質問を作る前に現在値を取って依頼と突き合わせる。**

```bash
python3 scripts/fetch_current.py --client foot --job 案件番号 --output /tmp/current.json
```

| 見るところ | 食い違いの例（実際に起きたもの） |
|---|---|
| ■勤務時間・シフト | 依頼`8:00-17:00` ↔ 掲載中`6:30～15:25、17:10～2:05`（2交替） |
| ■時給 | 依頼`2000円` ↔ 掲載中`1800円` |
| ■採用予定人数 | 依頼`1名` ↔ 掲載中`3名` |

**どちらかを黙って採用しない。**依頼側の書き間違いか、現場が変わったかのどちらかで、
原稿の問題ではない。黙って原稿にすると、応募者が面接に来てから発覚する。
0-1と同じ形で**1点だけ先に確認する**。

```text
先に1点だけ確認させてください。
いただいた勤務時間と、いま掲載中の勤務時間が食い違っています。

  ご依頼   ：8:00-17:00
  掲載中   ：6:30～15:25 ／ 17:10～2:05（2交替）

どちらが実態でしょうか。

  A. 8:00-17:00 の日勤に変わった（掲載中の記載を書き換えます）
  B. 掲載中の2交替が正しい（依頼の時間を読み替えます）
```

確認が取れたら、手順5の`make_entry_doc.py`に`--confirmed hours`（または`wage`）を付ける。
付けないと転記前チェックが止める。**確認せずに通す道は用意していない。**

### 0-3. 広告実績が渡されていたら、どの欄が効いていないかを先に見る

**AirWorkの有料広告の実績（求人単位のエクスポート）が手元にあるときだけ通す。**
無ければこの節を飛ばして0-4へ進む。**実績が無いことは着手の障害にしない。**

実績を先に見るのは、**直す欄を実測で決めるため**である。
見ないまま5案を作ると、クリックは取れているのに応募で落ちている求人の
キャッチコピーを書き直す、といったことが起きる。

```bash
python3 scripts/read_ads_performance.py --client foot \
    --spreadsheet '実績スプレッドシートのURL' \
    --sheet 'sponsor_求人単位_FooT' \
    --output /tmp/ads_performance.json
```

エクスポートには**案件番号が入っていない。**入っているのは「求人内容」列で、
中身は`雇用形態｜職種名｜求人キャッチコピー`の全角パイプ結合＝Joblistの
`job_type_jp`／`title`／`subtitle`をそのまま繋いだもの。スクリプトがJoblist側から
同じ文字列を組み立てて案件番号を引き当てる（FooT様の掲載中69件で一意に的中69件・
複数候補0件・該当なし0件を実測）。

「企業名」列は派遣元（株式会社FooT）で固定になる。Joblistの出向先企業名は掲載中の
全件が空で、**派遣先は勤務地でしか分からない。突き合わせに企業名は使わない。**

**判定は掲載中の求人の中央値を基準にした相対評価。**業種も媒体も違う外部の平均値は使わない。

| 診断 | 何が起きているか | 直す欄 |
|---|---|---|
| `ENTRY_WEAK`（入口が弱い） | クリック率が低い。検索一覧に出るのは雇用形態・職種名・キャッチだけ | **No.3 職種名 / No.33 キャッチコピー** |
| `BODY_WEAK`（中身が弱い） | クリックは取れるが応募開始率が低い。詳細を読んで離脱している | **No.7 仕事内容 / No.28 求める人材** |
| `BOTH_WEAK`（全面リライト） | 入口も中身も低い | **No.3 / No.33 / No.7 / No.28** |
| `OUTSIDE_COPY`（原稿の外） | 応募開始まで来て応募完了率だけ低い | **原稿を直さない。**選考フロー・応募フォーム側の話 |
| `INSUFFICIENT_DATA`（母数不足） | 表示数・クリック数が判定に足りない | **原稿を直さない。**もう少し配信してから見る |
| `HEALTHY` | 全指標が基準内 | **手をつけない** |

**`OUTSIDE_COPY`・`INSUFFICIENT_DATA`・`HEALTHY`のときは原稿をいじらない。**
そう判定されたことをフロントに1行で伝え、判断を返す。数字が動く見込みのない
書き直しを提案しない。依頼が「この求人を直してほしい」であっても同じで、
**直す理由が実績側に無いことを先に言う。**

雇用形態（No.1）はFROZENなので、**入口を直す手段は職種名とキャッチコピーの2つだけ**である。

出力の`records`は「中央値まで戻したときに増える応募数」の降順で並ぶ。
複数求人をまとめて相談されたときの**着手順はこの並びで決める。**率がいちばん低い
求人から直すと、表示数の少ない求人ばかりが並んで手間の割に応募が増えない。

出力の`winners`には、クリック率が中央値を大きく上回っている求人の
職種名とキャッチが入る。**手順3の5案を作るときの素材にする。**
勝っている書き方は、同じ会社・同じ媒体の中にしかない。

### 0-4. 同じ派遣先の他求人から事実を集める（人に聞く前）

**ヒアリングの前にここを通す。**同じ派遣先に既に出している求人には、
これから聞こうとしていることの答えが書かれていることが多い。

```bash
python3 scripts/collect_siblings.py --client foot \
    --site 派遣先名 --office 事業所名 \
    --job 今回の案件番号 --exclude 今回の案件番号 \
    --output /tmp/siblings.json
```

**`--job`（今回の案件番号）を必ず渡す。**渡すとその求人の郵便番号を引き、
**郵便番号が一致する求人だけ**を兄弟として集める。渡さないと派遣先名の
部分一致で探すことになり、取りこぼす。

求人メモの派遣先名は人が手で書いていて表記が割れる。2026-08-03 に実測したとき、
X市Y町の同じ事業所が Joblist 上で「甲山機工　リフト/X市/」「甲山本社」
「甲山リフト」「甲山検査」「簡潔甲山検査」…と13通りに割れていた。
名前で探すと**12件のうち1件しか拾えなかった**。郵便番号で探すと12件全部拾えた。

郵便番号は事業所も分ける。甲山グループは 1000001（X市）13件 と
1000002（Z地区）3件 にきれいに割れる。名前では区別できないが
郵便番号なら確実に分かれる。**別事業所の記述を混ぜると「そこには無い設備」を
原稿に書くことになる。**

郵便番号が引けないときは `--postcode` で直接指定する。どちらも無い場合は
名前の部分一致に落ちるが、そのとき警告が出る。

甲山機工（X市）で実測したとき、同じ派遣先に**他に16件**の求人があり、
ヒアリングで「不明」と返ってきた17問のうち**8問の答えがそこに書かれていた**。
使うリフトの種類、扱う荷物、作業の割合、手積みの有無、教育体制、班の人数、
設備・支給品、月収例。**聞かなくても書ける事実を聞きに行っていた。**

- 拾った事実の由来ラベルは`媒体データ`。`検証済み`ではない。
- 借りてよいのは**その派遣先の現場がどうなっているか**だけ。
  時給・人数・雇用形態といった**その求人の条件は借りない**（別案件の条件が混ざる）。
- 年代の記述（「20代・30代が活躍中」）は拾えても**応募資格には使えない**。
  職場情報タグ（No.23）と、本文では条件に翻訳して使う。
- 年代を探すときは**定型句だけを見ない**。「★30代、40代、50代が活躍中！」のような
  決まった文だけを数えると取りこぼす。2026-08-03 に甲山機工で「20代の記述はゼロ」と
  判断しかけたが、実際は同じ事業所の別求人の本文に
  「未経験から始めた方も多く、20代・30代を中心に活躍しています」があった。
  `collect_siblings.py` は本文を文単位に割って `age` カテゴリに集めるので、
  **出力の `age` を全部読む。**
- ここで埋まった項目は質問から外す。**残った不足だけを聞く。**

- 7項目で埋まる内容を質問し直さない。層1（派遣元）・層2（派遣先の事業所）のマスタで埋まる項目も除外する。

- **ヒアリング履歴スプレッドシートを先に読む。**

```bash
python3 scripts/hearing_log.py read --client foot \
    --site 派遣先名 --office 事業所名 --title 職種
```

**`--title`に■職種をそのまま渡す。省略しない。**層3は案件限りの回答なので、
同じ事業所でも仕事が違えば手積みの有無・資格・服装・立ち仕事かどうかは変わる。
`--title`があると、`read`が「今回の職種の回答」と「別の職種の案件の回答」を分けて出す。
渡さないと全部が「前回の回答」として出てきて、**別の仕事の事実が新しい原稿に混ざる。**

**出力のブロックをそのまま使う。**自分で層を判断し直さない。

| ブロック | 扱い |
|---|---|
| `■ 質問候補から外す（層1・層2で確認済み）` | **1問も聞かない。**層1は全社共通、層2は同じ事業所なら不変 |
| `■ 層3：すでに回答がある項目` | **前回回答を先に見せ、`変更がなければ回答不要`と添える。**質問の形にしない |
| `■ 層3：別の職種の案件の回答。流用しない` | **前回回答として見せない。**通常の質問として聞き直す |
| （どこにも出ない項目） | 通常の質問として聞く |

層は`references/clients/{client}/question-catalog.json`が正本で、`read`が照合して補正する。
スプレッドシートのE列は書き込み時の申告値なので、**E列だけを見て判断しない**。
`read`が「E列の層が実態と違う行を N 件補正しました」と出したら、スプレッドシート側も直す。

層3（年齢構成・作業量・資格の必須／歓迎）は案件が変われば変わりうるが、
**前回回答があるものを質問として並べない。**質問の形にすると、答えた側には
「もう答えたのにまた聞かれた」としか見えない。回答を先に見せて、違うときだけ言ってもらう。

```text
NG   2. フォークリフト運転技能講習修了は必須ですか、歓迎ですか。
        （前回この事業所では「歓迎」でした。今回も同じですか）

OK   ■ 前回の回答をそのまま使います（違うものだけ教えてください）
        ・フォークリフト運転技能講習修了 → 歓迎
        ・中型自動車免許 → 必須
```

**ただし職種・勤務地・時間帯が前回と変わる案件では、変わる項目だけ質問に戻してよい。**
例：前回が「4tトラックでの輸送」で今回が「倉庫内フォークリフト作業」なら、
中型自動車免許の要否は変わる可能性が高い。このときは**なぜ聞き直すのかを1行添える**。
理由なしで聞き直すと、上のNGと区別がつかない。

```text
OK   ・中型自動車免許 → 前回は「必須」でしたが、今回は倉庫内作業のため要否が変わりそうです。
       必須のままですか、不要ですか。
```

残った不明点のうち**原稿の訴求が変わるもの**を聞く。往復は1回で終える。

**質問数は「目標字数に届くか」で決める。上限は設けない。**
`references/appeal-formula.md`の`fieldTargets.roles`の各欄について、いま手元の確定事実だけで
`targetMin`に届くかを見積もり、**届かない欄をその欄で埋める質問に変換する**。
変換表は`question-catalog.json`の`fills`（欄→質問）と`hearing-protocol.md`の対応表にある。

往復が1回である以上、1回で聞く問数を絞ることに意味はない。絞れば、原稿が薄いまま出るか、
往復が2回になるかのどちらかにしかならない。**迷ったら聞く。**

| 順 | 聞くこと | 外すと何が壊れるか |
|---|---|---|
| 1 | 資格の必須／歓迎 | 職種名・求める人材・タグが総崩れになる |
| 2 | 年齢構成 | 20〜30代を集めるという依頼の目的に直結する |
| 3 | 手順1で出た原稿の矛盾 | 矛盾を残したまま出稿することになる |
| 4 | **1日の流れ**（`daily_flow`） | **仕事内容が400字に届かない。1問で工程・順序・休憩・繁閑を回収できる最効率の質問** |
| 5 | 扱う荷物・作業の内訳・使う機械 | 仕事内容が「荷物を運ぶ」で止まる |
| 6 | 教育期間・班の人数 | 未経験・ブランク層に向けた記述が一切書けない |
| 7 | 空調・設備・実際の月収 | 事実欄8個が全て100字未満のままになる |

年齢構成の回答は**応募資格に反映しない。**回答があった場合のみ職場情報タグとして使う
（詳細は`references/hearing-protocol.md`）。
- 派遣先へ問い合わせないと分からないことは含めない。フロントが即答できる粒度にする。
- **質問と5案を同時に出さない。**回答を受け取ってから手順3に進む。回答の内容で5案が変わるため、
  先に案を出すと作り直しになる。回答が「不明」ばかりでも、返ってきてから案を作る。
- 回答を受け取ったら、**未回答だった項目も含めて**ヒアリング履歴スプレッドシートに追記する。

```bash
# rows は [{"layer":"層3（案件限り）","question":"...","answer":"...","state":"未回答"}] 形式
python3 scripts/hearing_log.py append --client foot \
    --site 派遣先名 --office 事業所名 --job 12204054 --title 職種 \
    --rows /tmp/hearing_rows.json
```

  未回答も1行として残す。「聞いていない」と「聞いたが答えが返らなかった」を後から区別するため。
  **`--title`は必須。**J列に職種を残さないと、次のセッションの`read`が
  「この回答は今回の職種のものか」を判定できない。案件番号からJoblistを引く手もあるが、
  **新規案件はJoblistに行が無い**ので、仮の案件番号（`YYYYMMDD_派遣先名`）だと永久に判定できなくなる。
- **答えが返らない項目があっても原稿は完成させる。**未回答は欠陥ではなく想定内の状態として扱い、
  その項目を原稿に一切書かない。「たぶん20〜30代が多い」のような推測で埋めない。
- 未回答の既定処理（年齢構成→年齢タグを全削除、資格の必須/歓迎→厳しい側に倒す、など）と、
  質問文の雛形は`references/hearing-protocol.md`に固定してある。
- 手順1のlintを先に流している場合は、検出された矛盾（`残業なし`↔残業収入、`服装自由`↔`制服あり`など）
  の確認を同じ1回のやり取りに同梱する。矛盾をスキルが勝手に解消しない。

## 1. 公開前チェック（lint）

求人原稿に含まれる法令・媒体規約上の高リスク候補と、原稿についての説明・編集判断の混入をR1〜R10で検出する。原稿を自動修正しない。

```bash
node scripts/lint_copy.mjs \
  --input /tmp/normalized.json \
  --client foot \
  --output-dir /tmp
```

`/tmp/lint_result_YYYYMMDD.md`を確認し、`HIGH_RISK`と`WARN`を分けて求人番号・列・根拠を人間へ報告する。非掲載求人の検出は別セクションで確認する。

`--input`も`--output-dir`も`/tmp`配下でないと止まる（`scripts/secure_tmp.mjs`が門番）。正規化済みJoblistは求人本文そのものなので、Drive配下から読ませない。

## 2. タグの棚卸し

現行タグから削除推奨・追加推奨・リスクを診断する。内容確認書を省略してJoblistだけでも実行できる。

```bash
node scripts/audit_tags.mjs \
  --input /tmp/normalized.json \
  --contract /tmp/contract.json \
  --client foot \
  --output /tmp/tag_audit_raw_YYYYMMDD.json

node scripts/write_output.mjs \
  --tag-audit /tmp/tag_audit_raw_YYYYMMDD.json \
  --client foot \
  --date YYYYMMDD \
  --output-dir /tmp
```

`20代が多い`・`30代が多い`相当は、裏取り前の`CANDIDATE`として提案するだけで自動付与しない。
採用してよいのは次の2つが根拠になったときだけ。未回答・根拠なしなら全削除。

| 根拠 | 由来ラベル | 例 |
|---|---|---|
| ヒアリングで年齢構成の回答が返った | `確認済み` | 「20代・30代が中心」 |
| 同じ派遣先の兄弟求人に年代の記述がある（手順0-4） | `媒体データ` | 「未経験から始めた方も多く、20代・30代を中心に活躍しています」 |

**「20代・30代に来てほしい」は根拠にならない。**それは今の現場の事実ではなく採用側の希望である。
甲山機工のテストでは「現場の年代は不明。20代、30代がきて欲しい」と返ってきた。
この回答だけでタグを立てると、実態と違うタグを媒体に出すことになる。
ただし**同じ派遣先の他求人に年代の記述があれば、それは実態の記録なので使える。**
希望のほうは、その年代が反応する**条件**を本文に書くことで扱う（`references/writing-style.md`）。
`65U83 60代も応募可`や年齢表現を削除推奨としても、`AZ 年齢の制限=なし`を維持し、応募資格を全年齢のままとする。
**タグに何を立てても応募資格は動かさない。**この2つを混ぜない（`references/hearing-protocol.md`）。

確認するファイルは`/tmp/tag_audit_YYYYMMDD.md`。TSVとJSONは貼り付け・機械処理用として扱う。

## 3. A〜E の5案をつくる

**手順0の回答を受け取ってから着手する。**質問と5案を同時に出さない。

**着手前に手順0-1をもう一度確かめる。**■職種と■任せる仕事が食い違ったままなら、ここで書き始めない。
5案とも同じ矛盾を抱えて出てくるので、選んでもらっても直らない。手順0-1の形で先に確認する。

### 参照してよい素材の判断（由来ラベル）

「過去に作ったものは全部ダメ」でも「全部そのまま使う」でもない。**素材ごとに由来を見て判断する。**

| ラベル | 何か | 5案での扱い |
|---|---|---|
| `検証済み` | 出稿して応募が実際に増えた表現 | **最優先で使う。**近い形にアレンジして展開する |
| `確認済み` | 今回のヒアリングでYESが返った事実 | そのまま使う |
| `媒体データ` | Joblistの現行原稿（いま掲載中の内容） | 使う。ただし手順1の矛盾チェックを必ず通す |
| `前回推測` | 過去にスキルが埋めた表現。裏取りなし | **そのまま流用しない。**使うなら今回のヒアリングで再確認する |
| `未検証` | 出稿はしたが応募データがまだない | 使ってよい。ただし「刺さった証拠はない」と5案に明記する |

判断のフロー:

1. その表現の**根拠を出したのは誰か**。派遣先／フロントが言ったこと→`確認済み`。スキルが書いたこと→`前回推測`。
2. `前回推測`なら、**今回のヒアリングで裏が取れているか**。取れていなければ使わない。
3. `未検証`なら使ってよいが、**「効くと確認されたものではない」と明示する**。
   フロントが「前回と同じでいい」と判断する材料を奪わない。

**読む対象の既定は Joblist の現行原稿。**過去に生成した出稿用ドキュメントや中間JSONを、
無条件に「既存原稿」として読み込まない。読むなら上表のどのラベルかを判定してから使う。

### 5案の作り方

確認済みの事実だけを使い、A〜Eの5案を作る。**5案は2種類に分かれる。**

| 案 | 変えるもの | 構成 |
|---|---|---|
| A・B・C | **訴求軸**（何を言うか） | 説明型 |
| D | 軸はA〜Cで最も裏が取れたものを使い、**読ませ方**を変える | QUEST-悩み型（Qを悩みの列挙で行う） |
| E | 同上 | QUEST-数字型（Qを条件の断定で行う） |

A/B/Cは**軸を変える**（例 A=通勤と生活リズム／B=作業負荷／C=収入の読みやすさ）。
同じ軸の言い換えを3つ並べない。フロントは軸を選ぶのであって、語尾を選ぶのではない。
D/Eは軸ではなく**文章構成**で差をつける。QUESTの5段（Q絞り込み／U共感／E教育／S刺激／T行動）の
定義とテンプレートは`references/appeal-formula.md`の「本文の文章構成型（A〜E 5案の設計）」にある。
**E案はQ段に置く数字がすべて`検証済み`／`確認済み`のときだけ出す。**1つでも欠けたら
E案は出さず、テンプレの`{{E_SKIP_REASON}}`に理由を書く。

**5案とも、案ごとに変わるのは次の4欄だけ。**残りの欄は5案共通で1セットしか出さない
（案ごとに変えると事務員がどの案の値か取り違えるため）。
これは実装の都合ではなく仕様で、`appeal-formula.md`の`fieldTargets.roles`にある
`owner`（`variant`＝案ごと／`fact`＝5案共通）が正本。

| 区分 | 欄 |
|---|---|
| 案ごとに変える欄（variant・4欄） | No.3 職種名／No.33 キャッチコピー／No.7 仕事内容／No.28 求める人材 |
| 5案共通の事実欄（fact・11欄） | No.63 給与の補足／No.64 給与例／No.88 勤務時間・シフト／No.90 休日・休暇／No.24 職場環境の補足／No.153 試用・研修／No.97 福利厚生／No.155 選考について／No.99 契約更新期間／No.22 喫煙／No.95 社保なし理由 |
| 5案共通のその他（`fieldTargets`の15欄には入らない） | No.23 職場環境タグ／No.34 採用予定人数 |

**事実欄も5案と同時に生成される。**「案は本文4欄しか変わらないから中身が薄い」のではない。
事実欄が空のまま出てきたら、それは現在値にも素材にも根拠が無かったということで、
手順0-4（兄弟求人）とヒアリングに戻る合図である。字数のために推測で埋めない。

#### 広告実績の診断があるときは、5案の重心をそこに寄せる

手順0-3で`/tmp/ads_performance.json`を作っている場合、対象求人の`focusFields`を見る。
**5案の作り分けを、実測で弱いと出た欄に寄せる。**変える欄の数は増やさない
（variantは常に4欄）。変えるのは**どこで差をつけるか**である。

| 診断 | 5案の振り方 |
|---|---|
| `ENTRY_WEAK` | **No.3 職種名とNo.33 キャッチで5案を振る。**仕事内容・求める人材は事実の並べ替えに留め、案ごとの差は入口に集める |
| `BODY_WEAK` | **No.7 仕事内容とNo.28 求める人材で5案を振る。**職種名とキャッチは、いま取れているクリック率を壊さないよう表記を大きく変えない |
| `BOTH_WEAK` | 4欄すべてで振る。通常どおり |
| `OUTSIDE_COPY` / `INSUFFICIENT_DATA` / `HEALTHY` | **5案を作らない。**手順0-3の判定をそのまま伝えて止める |

`ENTRY_WEAK`のときにキャッチだけ書き直して仕事内容を触らないのではない。
**仕事内容は書くが、A〜Eの差をそこで作らない**ということである。
どの案を選んでも本文の質は同じで、選択の軸が入口に集まる。

`winners`（クリック率が中央値を大きく上回る求人の職種名・キャッチ）を素材にする。
ただし**文言をそのまま複製しない。**同じ会社の別求人と同じキャッチを出すと、
検索結果に同じ文字列が並んで両方の効きが落ちる。使うのは**構造**であって文字列ではない
（例：「時間の確定を先に置く」「金額を範囲でなく上限で書く」）。
なお`winners`は`媒体データ`であって`検証済み`ではない。そこに書かれた条件を
今回の求人の事実として持ち込まない（手順0-4の借用ルールと同じ）。

**各欄の目標文字数は`references/appeal-formula.md`のJSONブロック`fieldTargets.roles`が正本。**
散文の説明は同ファイルの「欄別の目標情報量」にある。上限は`limits.json`が正本。
**目標に届かないことより、推測を書くことのほうが悪い。**書けない欄は空欄のまま出し、
テンプレの「書かなかった事実欄と、その理由」に落とす。

### 文体は媒体本文として読ませる（文章を書く箇所すべて）

**正本は`references/writing-style.md`。案を書く前に読む。**
機械判定は`scripts/precheck_doc.py`のP10で、転記前に鳴る。

いちばん出やすいのが、**条件を並べる型（E案 QUEST-数字型）で書き手の手続きが本文に漏れる**形。

```text
NG  時給・勤務時間・休日を確認したうえで、リフト資格を活かしたい方に向いています。
OK  フォークリフト運転技能講習修了者。時給2000円、8:00〜17:00、土日休みの条件で、
    リフト資格を活かしたい方に向いています。倉庫内での出荷作業を、
    落ち着いて進められる方を歓迎します。
```

NGのほうは条件を**書かずに「確認しろ」と指示している**。E案のQ段は条件で絞る型なので、
**条件そのものを本文に置く**。「確認したうえで」「想定しています」「〜という形です」は使わない。

**情報が足りないときに説明で字数を埋めない。**同じ条件を4欄で言い換えると、
読者は同じことを4回読む。足りないなら手順0-4（兄弟求人）に戻って事実を取りに行く。

### 各欄に書くのは、そのまま媒体に載る文字列だけ

**12欄（案ごとの4欄＋共通の事実欄8個）に入れてよいのは、求職者が読む文章だけである。**
その文字列は事務員がAirWorkにそのまま貼る。原稿についての説明・編集判断・断り書きを
本文に混ぜると、事務員が「これは消すのか残すのか」を判断できず、納品物として成立しない。

| 本文に書かない（禁止） | 正しい置き場所 |
|---|---|
| 「今回の原稿では◯◯は入れません」 | テンプレ「確認していただきたい矛盾」／「5案に共通して外したもの」 |
| 「現行求人にある◯◯は今回は入れません」 | 同上 |
| 「◯◯は未確認のため書いていません」 | テンプレ「未確認のため書かなかった表現」／「書かなかった事実欄と、その理由」 |
| 「◯◯として出します」「◯◯で出稿します」 | 書かない。編集判断はチャット本文の前置きで述べる |

**手順0-1で矛盾を解決した結論は、社内向けの編集判断であって原稿ではない。**
結論そのものを本文に書かず、その結論に沿って書いた原稿だけを本文に置く。
例: 「輸送は入れない」と決めたら、本文は輸送に一切触れず倉庫内作業だけを書く。
「輸送は入れません」とは書かない。**求職者は元の原稿を知らないので、
「入れません」と書かれても何が変わったのか分からず、不安だけが残る。**

同じことが「未確認」にも当てはまる。書けない事実は**黙って書かないだけ**でよい。
「未確認のため書いていません」と本文に断ると、求職者には隠し事に見える。

機械的な検出は次の2箇所にある。どちらもHIGH_RISKなので、検出されたら本文から外す。

| 検出場所 | 何を見るか |
|---|---|
| `lint_copy.mjs` の**R10**（原稿についての説明・編集判断が本文に混入） | 出稿前の原稿全体 |
| `appeal-formula.md`の`forbiddenOutputPatterns`（`manuscript_self_reference`／`previous_posting_reference`／`editorial_exclusion`／`unverified_disclaimer`） | 生成文（`compose_variants.mjs`の出力） |

### 欄の役割を混ぜない

QUESTのT段（行動）を書くとき、**No.155 選考についての補足説明と同じ文を No.7 仕事内容に
繰り返さない。**No.155に応募後の手順（電話→説明→職場見学の日程→判断）を書き、
No.7の末尾は「職場見学できます」程度の一言にとどめる。
同じ文が2欄に並ぶと、事務員はどちらを貼るのが正なのか判断できない。

同じ理由で、職場の雰囲気（ひとりで進める・長く働く人が多い・社員食堂）はNo.24に寄せ、
No.7では繰り返さない。`compose_fields.mjs`がこの振り分けを持っているので、
生成結果を手で足すときも同じ分担を崩さない。機械判定は`precheck_doc.py`のP9（8字一致・3欄）。

### 5案は`compose_variants.mjs`が作る（自分で文章を書かない）

**ここで文章を書き起こさない。**AIが手で書くと、走らせるたびに文面が変わり、
根拠のない文（「残業は別途支給します」「試用期間なし」など、どこにも裏が無いもの）が混ざる。
実際に混ざった。だから15欄すべての文面生成を`compose_variants.mjs`に固定してある。

入力は4つで、手順0-4までで全部そろっている。

| 入力 | 出どころ |
|---|---|
| `--current` | `fetch_current.py`（対象求人の現在値） |
| `--siblings` | `collect_siblings.py`（同じ派遣先の他求人から集めた素材） |
| `--request` | 依頼フォーマット7項目をJSONにしたもの |
| `--hearing-ages` | ヒアリングで年齢構成の回答が返ったときだけ渡す（任意） |

```bash
node scripts/compose_variants.mjs \
  --job 1234567 \
  --current /tmp/current.json \
  --siblings /tmp/siblings.json \
  --request /tmp/request.json \
  --out /tmp/plan_candidates.json
```

出力`/tmp/plan_candidates.json`の中身:

| キー | 何が入るか |
|---|---|
| `common` | 5案共通の欄（事実欄11個＋No.23タグ＋No.34人数） |
| `variants[5]` | A〜E。`fields`（案ごとの4欄）と`charCount`（欄別の字数） |
| `meta.shortfalls` | 目標字数に届かなかった欄と不足字数。**手順4で何を聞くかの根拠になる** |
| `meta.blocked` | 使わなかった素材と、落とした理由 |
| `meta.evidence` | 本文の根拠にした文。事実チェックに「確認済みテキスト」として渡せる |
| `meta.ageEvidence` | 年代タグを立てた根拠（媒体データ／ヒアリング確認済み） |

**素材の大半は本文に通らない。**実測で193件中20件だけだった。これは不具合ではなく、
`lib/sibling_material.mjs`が表示先・確度・種別・職種近接度・出所フィールドの5つで
落としているからで、理由は`meta.blocked`に全部出る。
「素材が242件あるのに字数が足りない」と言われても、使えるのはこの20件だけである。

生成の根拠は次の順で探し、最初に見つかったところで止まる。
**どこにも無ければ書かない。字数のために説明文を足さない。**

1. 対象求人の現在値（`current.json`）
2. 依頼7項目とヒアリングで確認済みの回答（`request.json`）
3. 選別を通った兄弟素材（`sibling_material.mjs`が`usable`にしたもの）

### 案を選んでplanにする

フロントが1案選んだら、同じスクリプトで`apply_plan.py`が読む形に落とす。

```bash
node scripts/compose_variants.mjs \
  --from /tmp/plan_candidates.json \
  --select E \
  --plan-out /tmp/plan.json
```

`--select`はA〜Eの1文字。**「B案でいくがキャッチはD案」のような組み合わせ選択も許す。**
その場合は`--field`で「どの欄をどの案から取るか」を渡す。

```bash
node scripts/compose_variants.mjs \
  --from /tmp/plan_candidates.json \
  --select B --field 33:D \
  --plan-out /tmp/plan.json
```

`--field`は`No.:案`をカンマ区切りで並べる（`33:D,7:A`）。
どの欄をどの案から取ったかは実行時に出るので、`plan.json`を開いて確かめる必要はない。

**plan.jsonを手で開いて書き換えない。**貼り間違い・案の取り違えが誰にも気づかれないまま
ドキュメントまで通る。差し替えは必ず`--field`で指定する。

`--field`で指定できるのは案ごとに変わる4欄（No.3／No.33／No.7／No.28）だけ。
残りは5案とも同じ事実欄なので、指定すると「差し替えたつもりの空振り」を防ぐために止まる。

### `generate_variants.mjs`は5案生成に使わない

旧A/B運用の実装で、現行フローとは3点ズレている。

| ズレ | 実際の挙動 |
|---|---|
| 対象範囲 | 掲載中求人を**全件**処理する（1案件だけを指定できない） |
| 案の数 | A/B の**2案**しか返さない |
| 素材 | `--siblings`を読まない。兄弟求人の事実が1件も入らない |

`write_output.mjs --variants`が読む`assets/variants-template.md`も旧A/B用である。
欄別の不足字数（旧`fieldGaps`）は`compose_variants.mjs`の`meta.shortfalls`が代替する。

### 生成後に自分で見る（スクリプトが見ないもの）

`compose_variants.mjs`は競合データを読まない。定型文の組み立てに徹していて、
競合と比べた訴求の強弱までは判断できない。そこは案を眺めて自分で足す。

- `references/clients/{client}/competitors/_merged.md`がある場合は**セクション10・11・12**を読む。
  無い場合も停止しない。読むのは`_merged.md`の1本だけで、`_source/`と`INDEX.md`は人が読む材料。
  - §10 本文の書き出し8型 → No.7 仕事内容の書き出しの評価に使う（D案の悩み共感型はここが出典）。
  - §11 求める人材欄の型 → No.28 は「絞る欄」ではなく**応募ハードルを下げる欄**になっているか見る。
  - §12 条件欄・共通テンプレート欄の使い方 → 事実欄の書き分け（求人別／全求人同一）の確認に使う。
- 競合変数3・6・9の住居系、年齢・性別、雇用形態誤認、寮・家賃・奨励金、競合識別子が
  混ざっていないか見る。混ざっていたら本文から外す。
- 時給からの月額換算は、内容確認書行33・39〜43・45の必要実数が揃う場合だけ行う。推定値を使わない。
- 5案は同時掲載しない。**まず1案を選んで掲載する。**別案を試すのは効果を見たあとで、
  そのときだけ期間を分ける（前半2週間・後半2週間）。5案を並べる工程と効果測定の工程を混ぜない。
- 5案をチャットに並べるときは`assets/variants5-template.md`を使い、各案に軸・構成・効く相手と
  4欄（No.3職種名／No.33キャッチ／No.7仕事内容／No.28求める人材）を字数つきで載せる。
  D/E案にはQUESTの各段がどこに当たるかの表も付ける。5案共通の事実欄は末尾に1セットだけ出す。
  No.は**176項目版**の採番であることを明記する。
- 手順0で未回答だった項目は5案すべてで使わない。テンプレの「未回答だった項目」欄に明示する。

## 4. 足りない情報を洗い出す

内容確認書の未回答項目、ペルソナ確認質問、AirWork管理画面の未確認事項、効果測定で取得できる数字の確認事項を1つの依頼書にまとめる。

```bash
node scripts/make_request_sheet.mjs \
  --client foot \
  --contract /tmp/contract.json \
  --output-dir /tmp
```

`--contract`を省略すると全項目を未回答として扱う。指定した場合は`CONFIRMED_INTERNAL`の項目を依頼書から除く。生成物は`/tmp/data_request_foot_YYYYMMDD.md`だけに保存し、FooT様へ渡す前に人間が内容を確認する。

## 5. 選んだ案を出稿用ドキュメントにする

フロントが選んだ案（組み合わせ可）を176項目に流し込み、事務員がコピペで入稿できるGoogleドキュメントを作る。
指定フォルダに**新規作成**する。既存ファイルを上書きしない。
この工程に入る前に、手順0のヒアリング履歴への追記（`hearing_log.py append`）が済んでいることを確認する。

```bash
python3 scripts/fetch_current.py \
  --client foot \
  --job 案件番号 \
  --output /tmp/current.json

python3 scripts/apply_plan.py \
  --items references/clients/foot/items176-master.json \
  --plan /tmp/plan.json \
  --current /tmp/current.json \
  --output /tmp/items176_selected.json

python3 scripts/make_entry_doc.py \
  --items /tmp/items176_selected.json \
  --title 記載項目_派遣先名 \
  --tab 案件番号 \
  --client foot \
  --state /tmp/doc_state.json \
  --current /tmp/current.json \
  --request /tmp/request.json \
  --siblings /tmp/siblings.json

python3 scripts/style_entry_doc.py \
  --items /tmp/items176_selected.json \
  --state /tmp/doc_state.json
```

- **転記の前にチェックが走る。通らなければドキュメントは作られない。**
  `make_entry_doc.py`が`precheck_doc.py`を内部で必ず呼ぶ。**飛ばすオプションは無い。**
  チェックを外せるようにすると、急いでいるときほど外される。そして外したことは誰も覚えていない。

  | 引数 | 渡すと何を見られるようになるか | 省くと |
  |---|---|---|
  | `--current` | 掲載中より情報が減っていないか（P1）／契約条件が書き換わっていないか（P2） | その項目は外れる |
  | `--request` | 依頼の人数・時給・勤務時間が反映されているか（P3）／掲載中と食い違っていないか（P4） | 同上 |
  | `--siblings` | 兄弟求人に素材があるのに使い残していないか（P11） | 「未指定」と警告が出る |

  `--request`は依頼フォーマット7項目をそのままJSONにする。

  ```json
  {"site":"甲山機工","office":"X市","title":"リフトで出荷作業",
   "duty":"倉庫作業","hours":"8:00-17:00","wage":"2000円","hires":"1名"}
  ```

  例外を通すときは**明示する**。意図して掲載情報を減らすなら`--allow-shrink 24,64`、
  依頼と掲載中の食い違いをフロントに確認済みなら`--confirmed hours,wage`。
  **黙って通る道は用意していない。**
- **`--plan`は手作業で書かない。**手順3の`compose_variants.mjs --from ... --select ... --plan-out`が出す。
  手で書くと、案として見せた文とドキュメントに載る文がずれる。
- `--plan`の値は4種類ある。**「書けなかった」と「消したい」を同じ`""`で表さない。**

  | 値 | 意味 | 事務員転記の列に出るもの |
  |---|---|---|
  | 文字列 | この値を貼る | 値そのもの |
  | `""` | 情報が足りなくて書けなかった | **現在値をそのまま残す**（消さない） |
  | `"__DELETE__"` | 消すと決めた | `【削除】今の「◯◯」を消して空欄にする` |
  | `"__REVIEW__"` | 裏が取れないので人に決めさせる | `【要確認】…残すか消すかを決めてください` |

  以前は`""`を削除として扱っていた。甲山機工のテストでヒアリング20問中17問が「不明」で返り、
  掲載中の「土日休み・連休あり」「月収50万円以上可」「給与上限3000円」が全部消える指示になった。
  **情報が足りないときに既存の掲載内容を消すのは、リライトではなく破壊である。**
- 契約で決まっている項目（雇用形態・勤務地・給与形態・試用期間の条件）を`--plan`に入れると停止する。
  `--plan`のNo.が176項目マスタに無い場合も異常終了する。取りこぼしを黙って通さない。
- **ドキュメントには見出しも注記も入れない。**中身は176行の表だけにする。
  これは事務員にそのまま渡す作業指示であって、報告書ではない。ヒアリング結果・未回答項目・
  書かなかった表現・書き換えた項目のNo.は、事務員の手を動かすのに要らない情報である。
  経緯は手順0で**ヒアリング履歴スプレッドシートに残す**（`hearing_log.py append`）。
  フロント・FooT様へは**チャットの報告で伝える**。ドキュメントに書かない。
- タブ名は、既存求人なら手順0で引き当てた**案件番号**、新規案件なら`YYYYMMDD_派遣先名`。
  新規は出稿してAirWorkで採番されたあとに案件番号へリネームする。1案件1タブで、同じ派遣先の別案件はタブを足す。
- **1派遣先 = 1ドキュメント。ファイルを増やさない。**`make_entry_doc.py`が保存先を名前で検索し、
  あればそのドキュメントにタブを足す。同じ案件番号のタブが既にあれば中身を差し替える。
  だから同じ案件を何度作り直してもファイルもタブも増えない。
  ただし**同名ドキュメントが2本以上あると停止する**（どちらが正か決まらないまま書き足さないため）。
  そのときは片方を`bk`へ退避してから実行し直す。
- **「事務員転記」列に空セルを残さない。** 空欄は事務員に「入れないのか・消すのか・書き忘れなのか」を
  判断させることになる。`fetch_current.py`で取った現在値を`apply_plan.py --current`に渡すと、
  空セルが次のどれかに埋まる。1つでも空が残っていると`make_entry_doc.py`は起動時に落ちる。

  | 状態 | セルの中身 | 事務員の作業 | 背景色 |
  |---|---|---|---|
  | 貼る | 値そのもの | AirWorkの同じ項目にそのまま貼る | なし |
  | 消す | `【削除】今の「◯◯」を消して空欄にする` | いま入っている値を消す | 薄い黄色 |
  | 判断待ち | `【要確認】今の「◯◯」は裏が取れていません。残すか消すかを決めてください` | **手を止めてフロントに聞く** | 薄いピンク |
  | 触らない | `（入力なし）` | 何もしない（もとから空） | ライトグレー |
  | 触らない | `（社内管理用。触らない）` | 何もしない（求人メモ。単価が入る） | ライトグレー |

  色は「値の有無」ではなく**事務員が何をするか**で分ける。値の有無で塗ると、貼る・消す・触らないが
  同じ見た目になり、結局1行ずつ読ませることになる。
  **【要確認】をピンクで別扱いにするのは、事務員に判断させないため。**貼る・消すと同じ見た目にすると、
  その場で自分で決めてしまう。このスキルは事務員が判断しなくて済むことを前提に作っている。
- **`（変更なし）`は使わない（2026-08-02変更）。書き換えていない項目にも現在の掲載値をそのまま書く。**
  `（変更なし）`だと事務員はAirWorkの画面を開いて「今なんと入っているか」を自分で確かめることになり、
  転記ではなく確認作業になる。ドキュメントは長くなるが**上から順に貼れば終わる**ことを優先する。
  新規入稿は現在値が存在しないので`--current`を省く（全項目が`（入力なし）`＋planの値になる）。
- **ファイル名は`記載項目_{派遣先名}`だけ。**案件番号・案の記号・日付を入れると`check_title()`が起動時に弾く。
- **求人メモ（`job_offer_memo`）の中身をドキュメントに載せない。**請求単価/支払単価が入っている。
  `fetch_current.py`が伏せ字にし、`make_entry_doc.py`の`check_no_leak()`が最後にもう一度止める。
- ここで使うNo.は**176項目版**。Joblistスプレッドシートの265項目版とは採番が一致しない。
- 書式定数・タブID指定の3系統・実行上の落とし穴は`references/entry-doc-rules.md`にまとめてある。

作ったドキュメントのURLと、「貼る／消す／触らない」の行数内訳を人間へ報告する。媒体への入稿は人間が行う。

### 5-1. 出した指示は自動でJoblistへ記録される（人が起動しない）

**このセクションのコマンドを手で叩く必要はない。**上の4本を順に流せば記録も照合も勝手に走る。
覚えておくべきなのは「入稿指示ログというタブに記録が残る」ことと「状態が3つある」ことだけ。

| いつ | 何が起きるか | 呼び出し元 |
|---|---|---|
| `apply_plan.py`の実行後 | `<output>.meta.json`に**書き換えたNo.**が残る | — |
| `make_entry_doc.py`の実行後 | Joblistスプシの`入稿指示ログ`タブへ書き換えた項目を追記（状態=**未確認**） | `log_changes()` |
| 次に`fetch_current.py`を実行したとき | AirWorkの現在値と突き合わせ、**確認済み**／**差分あり**に更新 | `verify_pending()` |

- **書き戻し先はJoblistの`Sheet1`ではなく別タブ。**`Sheet1`はAirWorkのCSVをまるごと貼り替える運用なので、
  そこに列を足すと次の貼り替えで消える。`check_sheet_name()`が`Sheet1`系への書き込みを起動時に止める。
  タブ名は`config.json`の`spreadsheet.logSheetName`（既定`入稿指示ログ`）。
- **最初は必ず「未確認」から始まる。**スキルが書けるのは「こう入稿してほしい」という意図までで、
  事務員が実際にAirWorkへ貼ったかどうかは分からない。貼った前提で記録すると、
  次に`fetch_current.py`がそれを現在値として読み、`【削除】今の◯◯を消して`が
  存在しない値を消せという指示になる。事務員が一番混乱する壊れ方なのでやらない。
- Joblistが「**現実**」、入稿指示ログが「**意図**」。混ぜない。
  意図に裏が取れるのはAirWorkのエクスポートを貼り直したときだけである。
- 状態の遷移。**確認済みになった行は二度と再判定しない**（その指示の役目は終わり）。
  差分ありは次の照合で拾い直すので、事務員があとから貼れば確認済みに上がる。

  | 状態 | 意味 | 次にどうなるか |
  |---|---|---|
  | 未確認 | 指示を出したが、AirWorkに載ったか未確認 | 次の照合で判定 |
  | 確認済み | AirWorkの現在値が指示どおり | もう触らない |
  | 差分あり | 現在値が違う（未反映か、事務員が別の値で入稿） | J列に実値。次の照合で拾い直す |

- `fetch_current.py`の実行時に未確認・差分ありが残っていると
  `※ 前回の指示のうち N 件がまだ AirWork に反映されていません`と出る。
  **この警告が出ている現在値は前回の指示を含んでいない。**古い現実の上に次の原稿を積まないよう、
  フロントへ「N件が未反映」と伝えてから進める。
- **新規案件（AirWork未採番）は記録しない。**タブ名が`YYYYMMDD_派遣先名`のときは照合の相手がいないので、
  記録しても永遠に未確認で残るだけ。`make_entry_doc.py`が採番後に叩くコマンドを表示するので、
  AirWorkで番号が付いてからそれを実行する。
- ログの記録に失敗してもドキュメント生成は成功のまま終わる（警告だけ出る）。
  ここで落とすと、出来上がっているドキュメントを人が「失敗した」と受け取って作り直す。

## 失敗時

- 先にpreflightを実行し、`NG`の検査名、原因、表示された直し方を報告する。
- Joblist CSVがない、UTF-8でない、列順が違う、必須列が欠ける、設定JSONやルールJSONが不正な場合は処理を止める。
- `contract-map.json`に行35を含む範囲がある場合、未許可キー、未許可範囲、クライアント不一致がある場合は処理を止める。
- 内容確認書スプレッドシートへ疎通できない場合は`WARN`を出して先へ進み、内容確認書の項目は`MISSING`扱いになる。
- 未決事項を推測で埋めない。文字数上限は`limits.json`の暫定値であることを報告する。
- `20-30代の男女活躍中`を許可リストへ追加しない。
- 未許可企業名は架空と断定せず、照合が必要な`HIGH_RISK`候補として扱う。
